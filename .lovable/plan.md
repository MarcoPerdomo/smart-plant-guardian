# AI Transcriber + MCP Server for Verdant

## Goal
Give Verdant users a hands-free voice assistant inside the app, and expose the same plant-care actions to external AI assistants (ChatGPT, Claude, Cursor, etc.) through an MCP server.

## Capabilities summary

**Lovable AI Gateway already supports:**
- Speech-to-text via `POST /v1/audio/transcriptions` (`openai/gpt-4o-transcribe` by default, streaming SSE).
- Chat/tool calling via the Responses API (`openai/gpt-5.6-sol`) so the model can decide to call Verdant actions from natural language.
- Image generation (already used for plant catalog photos).

**Lovable MCP support:**
- `@lovable.dev/mcp-js` lets a TanStack Start app expose itself as an MCP server with OAuth-protected tools.
- The MCP route is auto-generated by a Vite plugin; we only author tool definitions and the OAuth consent screen.
- Because Verdant uses Lovable Cloud Auth (workspace identity), MCP OAuth tokens will have a different Supabase `sub` than the web app's Lovable identity JWT. Per-user tables must therefore key ownership on the verified `email` claim, not `user_id`, so both identities see the same plants.

## Phase 1 scope — plant care only

Both the voice assistant and the MCP server will support:
1. **List my plants** — nickname, location, overall status, last watered.
2. **Get plant insights** — latest sensor readings + most recent AI summary, or generate a fresh one.
3. **Log watering** — "I just watered my Monstera".
4. **Add a plant** — by common name; search catalog or create a new species profile with AI.
5. **Search the plant catalog** — find care info for any houseplant.

Marketplace, social, and weather actions are out of scope for Phase 1 but will reuse the same tooling layer.

## Database changes for MCP compatibility

Because the web plane uses Lovable identity JWTs and the MCP plane uses Supabase OAuth access tokens, the same person has two different `sub` values. We will migrate the Phase 1 tables to email-keyed ownership so both planes share rows:

- `user_plants`
- `sensor_readings`
- `watering_events`
- `ai_summaries`
- `plant_photos`
- `plant_weather_alerts`
- `profiles`

For each:
1. Add `user_email text NOT NULL DEFAULT lower(auth.jwt() ->> 'email')` (where missing).
2. Backfill from existing `user_id` via `auth.users.email`.
3. Add or replace owner policies to compare `user_email = lower(auth.jwt() ->> 'email')`.

The web app auth model is otherwise unchanged; only the MCP consent route mints a Supabase session.

## MCP server setup

1. Install `@lovable.dev/mcp-js` and `zod`.
2. Add `mcpPlugin()` to `vite.config.ts` (mounts at `/mcp`).
3. Create `src/lib/mcp/index.ts`:
   - `name: "verdant"`, `title: "Verdant"`.
   - `auth: auth.oauth.issuer({ issuer: "https://yfszbddvgowfniqvzkcg.supabase.co/auth/v1", acceptedAudiences: "authenticated" })`.
   - Register the five plant-care tools.
4. Create `src/lib/mcp/supabase.ts` with `supabaseForUser(ctx)` and `supabaseAnon()` factories.
5. Add `src/routes/[.]lovable.oauth.consent.tsx` using Sign In With Lovable (`lovable.auth.signInWithOAuth("lovable", { redirect_uri: window.location.href })`) so users can approve MCP clients.
6. Verify the Supabase OAuth 2.1 discovery document at `https://yfszbddvgowfniqvzkcg.supabase.co/auth/v1/.well-known/oauth-authorization-server` before claiming the connection works.

## In-app voice assistant

1. **Recording**: Web Audio API captures microphone PCM and encodes a complete mono WAV (16 kHz) on stop. Empty recordings are rejected client-side before upload.
2. **Backend**: `POST /api/chat` accepts either audio (multipart) or text JSON.
   - Audio path: forward WAV to Lovable AI Gateway `/v1/audio/transcriptions` with `stream: true`, then use the final transcript.
   - Text path: send transcript/user text to Lovable AI Gateway Responses API (`openai/gpt-5.6-sol`) with the plant-care tool definitions.
   - Execute tool calls by invoking the same `assistant/tools.ts` executors, then return the final assistant message as a streaming text response.
3. **Frontend**: A chat page with a message list, markdown rendering, and a microphone button. The first version is a dedicated `/chat` route under `_authenticated`; a floating widget can follow later.

## Shared tool layer

Both the voice assistant and MCP server use the same executor logic:

| Tool | Input | Action |
|------|-------|--------|
| `list_plants` | — | Returns user's plants with status + last watered. |
| `get_plant_insights` | `plant_id` or `nickname` | Latest readings, recent summary, or triggers `generateSummary`. |
| `log_watering` | `plant_id` or `nickname`, optional `amount_ml` | Inserts `watering_events` and updates `last_watered_at`. |
| `add_plant` | `nickname`, `name` (species) | Creates `user_plants` row, resolving species via `searchSpecies` / `lookupOrCreateSpecies`. |
| `search_catalog` | `q` | Returns matching `plant_species` with care highlights. |

## Testing and validation

1. Typecheck and build pass.
2. Run `app_mcp_server--extract_mcp_manifest` after MCP edits and confirm manifest regenerates.
3. Test `/api/chat` with text: "How is my Monstera doing?" → expects tool call + readable answer.
4. Test voice flow with a short WAV recording → expects transcript + response.
5. Verify MCP discovery endpoint returns tools after publish.
6. Confirm OAuth consent flow redirects correctly and the MCP server rejects unauthenticated requests.

## Risks and open decisions

- **Workspace identity + MCP**: Requires Supabase OAuth 2.1 authorization server to be enabled. This is configured by Lovable on publish; if the discovery document is not live after publish, the user must reconnect Supabase in Lovable and republish.
- **Email-keyed RLS migration**: Must backfill existing rows safely and keep the web app functioning for current users.
- **Audio handling**: WAV recording avoids browser/MediaRecorder fragmentation issues; iOS Safari compatibility must be tested.
- **Scope**: Keeping Phase 1 to plant care avoids over-complicating the first MCP consent screen and tool list.
